# Validation plan and release criteria

## Current release scope

The core command line is intended to be executable without a large scientific stack. Tests run on tiny synthetic fixtures and cover file parsing, validation failures, reports, and numerical methods. The GEO, Scanpy, read processing, Salmon, and R/Bioconductor paths are optional integrations with explicit dependency checks.

## Release checks

- `python -m unittest discover -s tests -v`
- `python scripts/validate_skills.py`
- `bash -n scripts/run_salmon_pipeline.sh`
- Exercise each core command on `examples/` and check outputs are nonempty.
- Check at least one malformed FASTA/FASTQ, one missing FASTQ, duplicate sample/gene identifiers, mismatched metadata, and an identifier-universe mismatch.
- On a release candidate, run the optional integration workflow using pinned external tool versions and a small fixture whose reference transcriptome and license are documented.

## Scientific validation still required for production

A passing software test is not proof that a complete study design or a biological conclusion is correct. Production use must validate the reference/annotation, gene identifiers, library chemistry, experimental design, sample exclusions, normalization/model assumptions, and interpretation against study-specific evidence. Keep logs and software versions.

## Future high-value contributions

1. A tiny, licensed public GEO series with expected sample fields and stable checksums.
2. A compact reference transcriptome plus Salmon index with clear redistribution permission, to test the actual quantification pipeline end-to-end.
3. Golden output files generated by pinned Scanpy/AnnData versions for a small multi-sample single-cell dataset.
4. `pre-commit` / linting, typed interfaces, performance tests on a synthetic large FASTQ, and container images for external tools.
5. Pathway collection download/version/license helpers, explicit Ensembl ID mapping, and GO/Reactome/KEGG ecosystem integrations without silently fetching large databases.
